2. Problem Interpretation and Product Boundary
What the platform is: a governance control system for mine-level evidence, compliance obligations, observations,
corrective actions, and management review.
What the platform is not: a mining production control system, payroll system, sensor platform, legal database, or
replacement for existing enterprise systems.
The implementation should concentrate on one measurable governance question: Which mine issues need attention
now, who owns them, what evidence supports the finding, and has the issue actually been closed?

Scope rule: every proposed feature must improve one of the following measurable outcomes: shorter

the MVP.

5. Detailed Functional Design
5.1 Compliance register
Each compliance requirement contains: requirement_id, mine_id, category, title, frequency, due_date, responsible_role,
responsible_user_id, status, evidence_document_id, source_reference, created_at and updated_at. Status is derived where
possible instead of manually typed. Example logic: compliant, due_soon, overdue, not_applicable.
5.2 Inspection capture
The inspector records mine, location, observation category, description, severity, GPS latitude and longitude, GPS
accuracy, timestamp, photo, and optional corrective-action suggestion. The API rejects incomplete submissions when
configured rules fail. High and Critical observations require a photo in the demo configuration.
5.3 Corrective action state machine
Use explicit states: OPEN -> ASSIGNED -> IN_PROGRESS -> VERIFICATION -> CLOSED. REOPENED is an exception
state. A state transition writes an audit event. Verification must be performed by a different authorized user than the action
owner.

10. AI, Risk Scoring and Anomaly Logic
The prototype should not claim that the mine score is a trained predictive model. With synthetic data and no labeled incident
outcome, the most defensible method is a configurable weighted index. The user-facing screen should explicitly call it a
Governance Risk Index.

Risk score = sum(component_score x weight). Each component is 0 to 100. Weights sum to 1.00. Store the component
values and reasons so the UI can explain the result.
Example explanation: Risk 78/100. Main contributors: compliance rate 45%, three High severity findings still open, four
actions overdue by more than 15 days. The score is a prioritization aid, not a claim that an incident will occur.
10.1 Recurring violation detection
Create a deterministic fingerprint such as category + mine_zone + contractor_id. Count occurrences in the last 90 days.
Flag recurring when count >= 3. Show the matched records so the user can inspect the evidence.
10.2 Production anomaly
Use a rolling 30-day z-score. Flag an anomaly when absolute z > 2.0, subject to a minimum history threshold such as 14
observations. With synthetic data, this is transparent and easy to test. The uploaded review specifically recommends rolling
z-score over Isolation Forest for the prototype. [Senior architect review, anomaly recommendation]
10.3 Explainable trend text
Compare current risk components to the previous period and generate a deterministic sentence. Example: "Risk increased
from 62 to 78 because corrective-action aging rose by 16 points." Do not require an LLM for this.

After the hackathon, the modular monolith can evolve without changing the product model. Keep the domain boundaries
stable even if deployment architecture changes.
Prototype
Production evolution

Explicitly do not implement blockchain, custom LLM assistant, IoT ingestion, Kubernetes, zone heatmaps, or a seven-role
UI in the hackathon MVP. These features can be revisited only after the core detect-to-close workflow is reliable. The senior
review supports these exclusions. [Senior architect review, scope recommendation]
FINAL BUILD ORDER
Schema and deterministic seed -> Auth/RBAC -> Compliance -> Inspection + evidence -> Corrective Action
+ audit -> Dashboard -> Explainable risk -> PWA offline sync -> GIS/alerts -> testing -> demo freeze.
Appendix A. Practical User Stories and Acceptance Criteria
ID
User story
Acceptance criteria
US-01
As an Inspector, I can record a field observation with GPS
and photo so the record has place and evidence.
Cannot submit High/Critical without photo and valid GPS accuracy;
successful submission creates server ID.
US-02
As an Inspector, I can save a field observation while offline
so reporting does not depend on live connectivity.
Inspection remains visible as pending; reconnect creates exactly one server
record.
US-03
As a Mine Manager, I can assign a corrective action with
owner and due date.
Action enters ASSIGNED state and audit event identifies manager.
US-04
As a Mine Manager, I can verify evidence and close an
action.
Owner cannot self-verify; another authorized manager can close.
US-05
As a Corporate Manager, I can see which mines need
attention first.
Dashboard ranks mines by configurable risk index and shows component
reasons.
US-06
As a Corporate Manager, I can inspect old overdue work.
Aging buckets let manager isolate actions older than 30 days.
US-07
As a reviewer, I can reconstruct who handled an action.
Timeline shows actor, action, timestamp and elapsed days.
US-08
As the demo operator, I can reset to a known data state.
Deterministic reset completes under 30 seconds and restores seeded
ranking.
